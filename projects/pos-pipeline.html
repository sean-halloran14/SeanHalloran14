A point-of-sale pipeline, ready before go-live

The company's restaurants are moving to a new point-of-sale system. Rather than port the old system's pipeline, I built one for the new system ahead of the switch, reusing the framework from my nightly pipeline rebuild, so the data and reports are ready the day sales move over.

14API endpoints, across two separately authorised APIs
~30cleaned and business tables, built by the same framework
7 daysre-pulled each night to catch late edits
Day onereport ready before any real sales arrive

The problem

The old point-of-sale data came through a workspace with its own pipelines, notebooks and storage, built the way the company's other early pipelines were. With the system being replaced, migrating that setup would mean rebuilding something about to be retired. What mattered was that the reports people rely on (sales, items, tip pools, time sheets) keep working on the new system's data.

What I built

Bronze: download. The new system's API works one restaurant at a time, so each request loops over the restaurants and merges the results into one raw file per day, tagged with the restaurant. Two separate API credentials sign in independently, each with its own token, and the client keeps to the vendor's rate limits and two different styles of paging.
Silver: clean. Orders, items, modifiers, payments, time entries, employees, jobs, menus and the restaurants' setup (discounts, service charges, tax rates, dining options) become typed Delta tables. Conventions are decided once: every percentage is stored as a fraction, even where the vendor sends some as 10 and others as 0.06.
Gold: combine. Business tables keep the old system's names and columns where reports depend on them, so existing reports can be repointed rather than rebuilt; where the new system has no equivalent the column is left empty and documented.

Details that matter

  • Late edits. Orders are fetched by business day and the last seven days are pulled again each night, catching tips adjusted and items voided after the fact.
  • Built before the data existed. The restaurants are still in test mode, so tables built on sales simply warn "no data yet" and succeed, instead of failing every night until cutover.
  • Menu coverage. Every item and modifier set up in the system is compared with the published menus, and the report flags items that aren't on any menu.
  • Same safety net. The run logging, gap filling and test-copy workflow from the nightly pipeline come with the framework for free.

Where it's going

This was the first pipeline to reuse the framework, and it showed the shared code drifting between copies. My plan to package that framework as a versioned library, installed by each pipeline at a pinned version, has been approved, so the next migrations start from one tested source.
