Pipelines · Data engineering

One nightly pipeline for a company's sales data

A vending, micro-market and office-coffee company's reporting depended on dozens of separately scheduled jobs that had grown one report at a time. I rebuilt it as a single object-oriented Python pipeline in Microsoft Fabric that runs once a night, checks itself, and repairs its own gaps.

The problem

The original workspace grew the natural way: each new report got its own small chain, a pipeline to download it, often a dataflow to clean it, a notebook to reshape it, and a separate "historical" copy to reload past months. Each piece solved a real need, but together they added up to 77 pipelines, about 30 dataflows and 43 notebooks.

  • Hard to check. Confirming that a night had loaded meant looking across 46 separate run histories.
  • Expensive. Over two weeks the workspace ran 1,149 jobs, roughly 6 hours of run time a day on a capacity shared with every other team.
  • Rules spread out. Logic such as which invoices count as a sale or how waste is valued lived across pipeline settings, dataflow steps and notebooks.
  • Manual recovery. A longer outage had to be repaired by hand, and changes were tested next to the live jobs.

What I built

One job works through every table in order each night, in three layers (a medallion architecture):

Bronze: download. Fetches 56 reports from the vendor's REST API and saves each response untouched as JSON, so any table can be rebuilt without asking the vendor again.
Silver: clean. Turns each report into a typed, tidy Delta table (58 of them) with consistent names, dates and exact decimal money, plus lineage columns saying which file and day each row came from.
Gold: combine. Builds 15 business tables, such as daily vending, market and office-coffee sales, waste, shrink and commission in one table, with every rule written once and documented.

The design is object-oriented: a workspace class, a class per API report and a class per table, each inheriting downloading, cleaning, history, checks and logging. Adding a new report means writing one short class and adding it to the nightly list.

Moving over safely

The old workspace kept running while the new one was built, so nobody's reports broke along the way.

  • Same rules, new home. The business rules the original had established were kept, then gathered into one documented place instead of being spread across tools.
  • Built in a test copy. Everything was developed against separate dev tables and files, so production was never touched by unfinished work.
  • Checked value by value. Comparison notebooks matched the new tables against the original workspace, table by table and value by value, before any report switched over.
  • History rebuilt from source. Every dated report back to January 2024 was backfilled from the vendor and saved untouched, so any table can be rebuilt at any time.
  • A pattern to repeat. The design is written up so the company's other data sources can move the same way; the CRM data is already being rebuilt along these lines.

How it looks after itself

  • Reports on itself. Every run logs each report and table: what loaded, row counts, freshness, and warnings such as a sudden drop in rows. A Power BI diagnostics report shows it, and if anything fails the whole run is marked failed so it can't be missed.
  • Fills its own gaps. Each night it looks for any missing day or month back to January 2024 and fetches up to 14 of them, so a missed night is fixed by the next run.
  • Waits for complete inputs. If a download fails, the tables that depend on it keep yesterday's data instead of being rebuilt from partial inputs.
  • Test copy first. Every change runs first against separate dev tables, is compared value by value with the original workspace and production, and only then is promoted.
  • Works with the people who own the data. A supplier order calendar the operations team keeps in Excel is read every night and checked against the source system; mismatches land in a report for them to fix.

Results

  • Every nightly run has succeeded since go-live, finishing in about 13 minutes.
  • The new tables were checked value by value against the original before reports switched over.
  • Retiring the old schedules frees up to about 6 hours of daily run time on the capacity the company pays for.
  • I wrote a 50-page developer reference and an 18-page analyst guide, so others can query the tables, build reports and add features safely.
  • The same pattern is now being applied to the company's other data sources.

Documentation

I wrote the project up for three audiences, so each can get what they need without reading code:

  • Managers: a plain-language overview of how the new setup builds on the original, with the two side by side and what it means for the business.
  • Analysts: an 18-page guide with ground rules, recipes (top accounts, waste rates, "did last night's run load?"), how to build Power BI reports on the tables, and how to add a table, column or report safely through the test copy.
  • Developers: a 50-page reference covering every business rule, the nightly run step by step, and every class and method, plus known quirks and open questions.
