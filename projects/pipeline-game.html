A company's sales reporting used to run on 46 separate jobs. I rebuilt it as one Python pipeline that runs every night, checks itself and fixes its own gaps. Play through one night of it.

Level 1 of 6 · The problem

The tangle

It's 7 a.m. Did last night's data load? Every report has its own scheduled jobs, and each keeps its own run history. Click jobs to check them.

What I did

46 schedules became one

The original workspace grew one report at a time: each new report got its own chain (a pipeline to download it, often a dataflow to clean it, a notebook to reshape it, and a separate "historical" copy). Altogether that was 77 pipelines, about 30 dataflows and 43 notebooks on 46 schedules, using about 6 hours of run time a day on capacity shared with every other team.

I replaced all of it with a single object-oriented Python pipeline in Microsoft Fabric that runs once a night and logs everything to one place.

Level 2 of 6 · Bronze: download

Catch the downloads

The vendor's API is sending tonight's reports. Move the orb to catch them (mouse, finger or arrow keys) and they're saved to bronze exactly as they arrived. Grey ones came back empty. Catching one logs a warning, but it doesn't count.

What I did

Keep the raw copy first

Each night the pipeline fetches 56 reports from the vendor's REST API and saves each response untouched as JSON. That's the bronze layer. Because the raw copy is kept, any table can be rebuilt without asking the vendor again. Every dated report back to January 2024 was backfilled the same way.

Downloads that are missed don't need fixing by hand: the next night looks for missing days and fetches them (you'll see this in level 5). Empty downloads are flagged as warnings in the run log.

Level 3 of 6 · Silver: clean

Clean the rows

Raw reports are messy. Pick the right fix for each field before it goes into a silver table.


        

        

        

        

          
        

      

      

        
What I did

        
58 tidy, typed tables

        
The silver layer turns each raw report into a typed Delta table, 58 of them, with consistent names, real dates and exact decimal money, plus lineage columns saying which file and day each row came from. The cleaning is written in Polars and DuckDB SQL and saved with delta-rs.

        
      

      
    


    
    

      

        
Level 4 of 6 · Object-oriented design

        
Add a new report

        
Operations wants a new report: office coffee deliveries. Every report class inherits from Endpoint. Pick only the parts you'd have to write yourself, then write the class.

        

          
          

            
What does CoffeeDeliveries need?

            

            

              
            

          

        

        
    
        
      
    
      
    
        
    What I did
    
        
    One short class per report
    
        
    The pipeline is object-oriented: a workspace class for paths and settings, a class per API report and a class per table. Each inherits downloading, cleaning, history, checks and logging from its base class, so every report behaves the same way.
    
        
    Adding a report means writing one short class and adding it to the nightly list, and every business rule is written once in one documented place instead of spread across pipeline settings, dataflow steps and notebooks.

      What I did
      
        
      A pipeline that looks after itself
      
        
        
          
      • Waits for complete inputs. If a download fails, the tables that depend on it keep yesterday's data instead of being rebuilt from partial inputs.
        • 
          
      • Reports on itself. Every run logs each report and table: what loaded, row counts, freshness, and warnings such as a sudden drop in rows. If anything fails, the whole run is marked failed so it can't be missed, and a Power BI diagnostics report shows it all.
        • 
          
      • Fills its own gaps. Each night it looks back to January 2024 for any missing day or month and fetches up to 14 of them, so a missed night is fixed by the next run.
        • 
        
      
        
      The failure in this level is made up so you can see what would happen. In real life every nightly run has succeeded since go-live, finishing in about 13 minutes.

      What I did
      
        
      Same rules, new home
      
        
        
          
      • Built in a test copy. The old workspace kept running while I developed against separate dev tables, so nobody's reports broke along the way.
        • 
          
      • Checked value by value. Comparison notebooks matched every new table against the original, and each difference was traced to its cause before any report switched over.
        • 
          
      • Same rules kept. The business rules the original had established were kept, then gathered into one documented place.
