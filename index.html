    • One nightly pipeline for a company's sales data

      A vending and food-service company's reporting ran on 46 separately scheduled pipelines, dataflows and notebooks that had grown one report at a time. I rebuilt it as a single object-oriented Python pipeline in Microsoft Fabric: each night it downloads 56 API reports, keeps the raw copies, and builds 58 cleaned and 15 business tables, checking and logging itself as it goes. It runs in about 13 minutes instead of roughly 6 hours of daily run time, fills in missed days on its own, and keeps every business rule in one documented place.

    • Migrating a live workspace without breaking reports

      Moving a company's live reporting onto a new design without breaking anyone's reports. I rebuilt the work in a separate test copy, kept the business rules the original had established, and compared the new tables with the old ones value by value while both ran side by side. The approach is now a repeatable pattern: the company's new point-of-sale data was the first to reuse it, and my plan to package the shared framework as a versioned library, so every pipeline stays in step, has been approved.

    • A pipeline that checks itself and its data

      Checking whether a night's data had loaded used to mean looking through 46 run histories. I built diagnostics into the pipeline: every run logs each report and table (rows loaded, freshness, and warnings such as a sudden drop in rows) and fails as a whole if anything is missing. I then added a data-quality stage that flags suspicious rows instead of deleting them, such as dates decades in the future, duplicates and products with no name, and traces each one back to the raw record it came from. Both feed Power BI reports, including a run-history page that exposed a download routinely brushing against its time limit.

    • Writing it down so others can use it

      A data platform only helps if people can use it and change it safely. For the pipeline rebuild I wrote a plain-language overview for managers, an 18-page analyst guide with recipes for querying the tables and building reports, and a 50-page developer reference covering every business rule, table and class. Then I made the pipeline document itself: each night it builds a lineage diagram of how every table feeds the next, and documentation pages generated from the code's own classes, comments and SQL, so the docs can't drift from what actually runs.

    • A point-of-sale pipeline, ready before go-live

      When the company's restaurants began moving to a new point-of-sale system, I built its data pipeline ahead of the switch by reusing the framework from the nightly pipeline. It signs in with two separate API credentials, merges per-restaurant requests into one raw file a day, keeps to the vendor's rate limits and paging, and re-pulls the last week to catch late edits like adjusted tips and voids. Its business tables keep the old system's column names so existing reports can be repointed, and a Power BI sales and menu-setup report, which flags items that aren't on any menu, is ready for cutover.
